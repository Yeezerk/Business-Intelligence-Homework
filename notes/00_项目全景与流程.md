## 1. 一个ML项目的完整生命周期

```
问题定义 → 数据获取 → EDA → 数据预处理 → 基线模型 → 
模型设计与实现 → 训练与调优 → 评估 → 可解释性分析 → 部署/交付
```

每个阶段的产出物：

| 阶段 | 输入 | 产出 | 本项目对应文件 |
|------|------|------|-------------|
| 问题定义 | 业务需求 | 研究问题、评估标准 | 论文引言 |
| 数据获取 | Kaggle/数据库 | 原始数据 | `01_download.py` |
| EDA | 原始数据 | 数据报告、可视化 | `02_eda.py` → `outputs/figures/` |
| 预处理 | 原始数据 | 清洗后的训练/验证/测试集 | `03_preprocess.py` → `outputs/processed/` |
| 基线 | 处理后数据 | 基线指标 | `04_train_baselines.py` → `outputs/results/` |
| 模型实现 | 论文/架构设计 | 模型代码 | `models/*.py` |
| 训练调优 | 模型+数据 | 训练好的模型 | `05_train_neural.py` → `outputs/models/` |
| 评估 | 模型+测试集 | 指标、图表 | `06_evaluate.py` → `outputs/figures/` |
| 可解释性 | 模型+测试集 | SHAP图、注意力图 | `07_interpret.py` |
| 论文 | 所有结果 | LaTeX + PDF | `paper/` |

## 2. 本项目的架构设计

### 2.1 为什么这样组织代码？

核心原则：**关注点分离 (Separation of Concerns)**

```
code/
├── data/          ← 只关心"数据从哪里来、变成什么样"
├── models/        ← 只关心"模型长什么样"（纯PyTorch nn.Module）
├── training/      ← 只关心"怎么训练"（与具体模型解耦）
├── 04_*.py        ← 编排脚本：加载数据→创建模型→训练→保存
├── 06_*.py        ← 评估脚本：加载模型→跑测试集→画图
└── 07_*.py        ← 可解释性脚本：SHAP + 注意力
```

**好处**：
- 改模型结构不改训练逻辑（`models/` 和 `training/` 独立）
- 换数据集只需改 `data/` 目录
- 加新模型只需在 `models/` 加一个文件，其余复用

### 2.3 运行顺序

```bash
# Step 1: 获取数据
python code/data/01_download.py

# Step 2: 探索数据（不依赖后续步骤）
python code/data/02_eda.py

# Step 3: 预处理（为训练准备tensor）
python code/data/03_preprocess.py

# Step 4: 传统基线（验证数据管道正常）
python code/04_train_baselines.py

# Step 5: 神经网络（核心实验）
python code/05_train_neural.py

# Step 6: 评估可视化（论文图表）
python code/06_evaluate.py

# Step 7: 可解释性（商业分析）
python code/07_interpret.py
```

## 3. 关键设计决策

### 3.1 为什么用 Focal Loss 而不是 SMOTE？

SMOTE 生成合成样本，在特征空间中插值。问题：
- 增加训练时间（更多样本）
- 生成的低质量合成样本可能误导模型
- 对深度模型不如对树模型有效

Focal Loss 直接修改损失函数：**不改变数据，改变模型关注什么**
- 容易分类的样本损失权重降低
- 难分类的样本（通常是少数类）获得更多关注
- 无需额外计算开销

详见 `notes/02_Focal_Loss深度解析.md`

### 3.2 为什么 AUPRC 而不是 ROC-AUC？

在正类仅占 0.1%-1% 的数据上：
- ROC-AUC 的计算中，True Negative（正确预测的正常交易）占主导
- 即使模型将所有交易预测为"正常"，ROC-AUC 仍可接近 0.99
- PR 曲线聚焦于正类（欺诈）的预测质量，对类别分布敏感

详见 `notes/06_评估指标的商业视角.md`
